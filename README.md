# 酒店容量与超售处置

按住宿日和房型复盘一家酒店在某个观察时点的可售、已订和实际占用，并把超售时的升级安排逐条追到约束上。

```bash
npm install
npm run dev       # 开发服务器
npm run test      # 27 条模型 / 交互测试
npm run build     # tsc -b && vite build
```

## 页面结构

| 区块 | 作用 |
| --- | --- |
| 观察时点 | 顶部 `datetime-local`，±1 天或回到默认时点；所有回放都用这个时点重算 |
| 视图切换 | 可售 / 已订（需求视角）与 可售 / 已安置（落房视角） |
| 可售日历 | 房型 × 住宿日热力表，格内大字为可售、小字为已订/可售；标记超售、封房、后录封房、未安置、实际 |
| 超售安置优先级 | 会员等级 / 渠道 / 创建时间 / 入住时长，可上下调序 |
| 升级规则 | 启用关系、单晚成本、最低会员等级、单晚成本上限；未启用的链路不参与安置 |
| 安置明细 | 每单的最终房型、已安置/未安置、升级成本、标签（升级 / 拆房拆晚 / 实际入住 / 提前退房释放） |
| 取消率情景抽样 | 固定种子重复抽样，P10–P90 区间与未安置房间数直方图；实际回放与模拟结果分开展示 |
| 导入 / 封房 | 预订与封房 CSV 导入、模板、校验消息 |
| 数据问题 | 日期、房量、封房超量、重复 ID、实际变更缺少记录时间等校验 |

点任一格打开当晚明细：按房型拆解容量，再逐单列出该晚的占用、释放和「查看约束追溯」。点「打开整单」进入预订检查器，按住宿日查看每一晚的房型、间数与追溯链。

## 核心口径

- **半开区间**：住宿占 `[arrival, departure)`，封房扣 `[startDate, endDate)`，窗口取 `[windowStart, windowEnd)`。入住日算、退房日不算；界面上住宿区间统一显示到退房日并注明「退房日不计」。
- **按住宿日而不是按订单汇总**：需求先摊到 `住宿日 | 房型` 上，再按该粒度落房。跨夜单自然只占它经过的夜晚。
- **观察时点回放**：`asOf` 之前创建的预订才算数；`cancelledAt > asOf` 的预订在该时点仍算已订，`cancelledAt <= asOf` 的才剔除。封房同理看 `recordedAt`，后录封房只记入 `lateBlockIds` 并在格子上打「后录封房」，不从当时的容量里扣。
- **实际入住是既成事实**：带 `actualRecordedAt` 且不晚于 `asOf` 的实际到店 / 离店 / 换房会替换计划区间，先于计划需求锁定占房，不参与重新安置。晚于 `asOf` 的实际变更不用于回放，只在备注里说明「本次回放按计划日期占用」——不用后来知道的结果美化历史。
- **提前退房**：实际离店早于计划，多出的夜晚进入 `releasedNights`，当晚明细显示「已释放（提前退房）」，容量重新可售。
- **延住**：实际离店晚于计划，按实际日期继续占房。
- **拆房 / 合并**：需求按 `住宿日 | 房型` 去重，同一晚同房型重叠段取最大间数，不同房型分别计；人数从不跨段相加。`mergeGroupId` 相同的记录只有 `mergePrimary` 那一条计入容量，其余在问题面板里提示。
- **不补不存在的房量**：安置只从真实剩余房量里取，放不下的部分以 `assignedTypeId: null` 记为未安置，绝不写回某个房型充数。未安置的追溯会列出原因：无升级关系 / 关系未启用 / 会员等级不够 / 超出单晚成本上限 / 房量已被更高优先级占满。

## 安置与升级

1. 实际入住先锁房。
2. 计划需求按 `priority` 顺序（默认 会员等级 → 渠道 → 创建时间 → 入住时长）逐段安置，同优先级按创建时间与单号稳定排序。
3. 每段优先原房型；原房型不足时，沿升级图（支持 STD → DLX → SUP 多跳）取所有配置链路，按 `成本 → 跳数 → 房型顺序` 排序，过滤掉未启用和 `minTier` 不满足的链路，以及超过 `maxUpgradeCostPerNight` 的链路。
4. 一段可以拆到多个房型：先填满原房型，再按链路顺序填空房。每一步都产出一条 trace，可在明细里核对。
5. 安置后再按最终房型汇总「已安置」；未安置只出现在缺口，不改变任何房型的可售数。

## CSV 字段

预订（一行一段，按 `bookingCode` 合并）：

```
bookingCode,segmentId,guestName,channel,tier,createdAt,roomTypeId,arrival,departure,rooms,adults,children,cancelledAt,mergeGroupId,mergePrimary,actualArrival,actualDeparture,actualRoomTypeId,actualRecordedAt,notes
```

封房（`endDate` 不含当日，`roomTypeId` 留空表示全房型）：

```
blockId,reason,roomTypeId,startDate,endDate,roomsBlocked,note,recordedAt
```

`reason` 取 `maintenance` / `lock`（也接受「维修」「锁房」）；`actual*` 字段必须与 `actualRecordedAt` 同时出现，否则导入时给出警告。完整数据集也可以用 `importDatasetJson` 走 JSON 导入 / 导出。

## 样本数据覆盖

窗口 2026-11-12 → 2026-11-26，默认观察时点 2026-11-14 08:00：跨 4 晚预订、同单拆分到多房型、合并组重复行、观察时点之后才取消（R-1006）与之前已取消（R-1007）、观察时点后才记录的实际延住（R-1012）与之前已记录的提前退房（R-1011）、按日期维修与临时锁房（含 11/14 15:00 才录入的后录封房 BLK-3）、FAM → SUP 未启用导致的 2 间未安置、STD → SUP 仅限金卡以上的受限链路。默认参数下：窗口 360 间夜，已订 144 间夜，已安置 142，实际入住 2，升级 18 间 / ¥2,580，未安置 2 间（R-1013 的 11/17、11/18）。
